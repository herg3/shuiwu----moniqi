# 从一个 UI 截图还原出可装到手机的 App

> 本文是这个仓库的技术说明。核心问题只有一个：**手上有几张别人 App 的截图，能不能用纯 HTML/CSS 复刻到像素级，并打包成能装在安卓手机上的应用。**
>
> 结论先说：能，但靠的不是"看着像"，是一套能量化、能收敛的测量闭环。

---

## 一、为什么大多数"看截图写 UI"会失败

最直觉的做法是：看图 → 用文字描述（"顶部有个蓝色渐变卡片，圆角大概 12px"）→ 交给代码生成。

这条路有一个致命缺陷：**它是一次性有损压缩**。

文字能表达"有一个蓝色卡片"，表达不了：

- 那个蓝的 hex 值（`#1677FF` 还是 `#2B6DE5`）
- 圆角半径（12 还是 13.33）
- 字号 / 行高 / 字距 / 字重的组合
- 元素之间的间距节奏
- 分割线的透明度

更严重的是：**描述写完，真值就丢了**。之后代码只能跟自己的描述比，没有任何东西能告诉你"现在偏了 12 像素"。于是越修越偏。

正确的做法是把截图留在环里：

```
截图（真值）
    ↓
手写 HTML/CSS
    ↓
同参数 headless 渲染截图
    ↓
像素 diff + 差异热区
    ↓
按热区改 CSS ──┐
    ↑__________│   （循环，直到收敛）
```

三个关键点：

1. **不做文字转述**。看原图直接写代码，图始终是唯一真值。
2. **几何值从像素里量**，不看图猜。颜色、坐标、字号都是能从截图里读出来的硬数字。
3. **每改一轮重新截图算分**，收敛判据是量化指标，不是感觉。

## 二、量几何：从截图里读出数字

原图是 `1179×2556` @3x（iPhone 尺寸）。逻辑像素是 `393×852`。所有 CSS 值都按逻辑像素写，这样 1 CSS px = 3 物理 px。

测量工具在 `tools/`：

- `slice.py` — 彩色图标抠图：在选定区域内从四边 flood fill 去掉连通背景，保留内部图形，导出透明 PNG 素材
- `measure.py` — 对原图和渲染图做同样的文字 bbox 测量，输出并排对比（拿到文字实际占据的矩形范围，而不是“看起来差不多”）

产出的是这种数字（真实取自本项目首页）：

```css
/* 实测 y0-310 → 103.33px */
.hero{position:absolute;left:0;top:0;width:100%;height:103.33px;}

/* 入口卡片：实测 left13 / top147.67 / 106×116 / r21 */
.qcard{position:absolute;top:44.34px;width:106px;height:116px;
       border-radius:var(--r-card);background:#fff;overflow:hidden;}
```

注意那些 `.33` / `.67` —— 这不是凑数，是 3x 截图换算成逻辑像素时必然出现的非整数。用整数近似，在 3 倍屏上就是 1-2 物理像素的整圈误差。

## 三、渲染截图：参数必须严格对齐

```bash
node tools/shot.js index.html mine_index.png
```

关键参数：`viewport: 393×852`，`deviceScaleFactor: 3`。任何一个不对，diff 全无意义。

**一个踩过的坑**：flex 居中在 3x 下会产生 0.5 物理像素偏移，导致所有元素边缘整圈报差异。所以 `shot.js` 会在截图前注入强制对齐样式，把 `.phone` 固定到 `(0,0)`：

```js
await page.addStyleTag({ content:
  'body{display:block!important;margin:0!important;padding:0!important;overflow:hidden!important;}' +
  '.phone{position:absolute!important;left:0!important;top:0!important;}' });
```

不做这一步，你会看到"每个边缘都差一点"，然后去调一堆本来没错的 CSS。

## 四、比对：把差异变成一个数

```bash
python tools/compare.py <原图.png> mine_index.png
```

输出三样东西：

1. **平均通道差**（0-255）：整页的总体偏离
2. **逐像素完全一致占比**
3. **32×32 css 块热区**：按 mean 降序列出最差的块及其 css 坐标（最多 28 条）
4. **分区统计**：按视觉区块（状态栏 / 搜索 / 入口卡片 / banner / tabbar）分别给 mean 和「>24 占比」

同时把差异图存成 `shots/diff_<文件名>.png`，通红的地方就是问题所在，可以直接看。

然后按最热的坐标回去改对应元素。这个循环能收敛，因为热区会精确指向问题元素。

本项目实际数据：

| 页面 | 平均通道差 | 逐像素完全一致 | 显著差异 |
|---|---|---|---|
| index.html | 10.70 / 255 | 60.31% | 9.60% |
| income.html | 7.56 / 255 | 86.80% | 6.18% |

## 五、最有价值的一节：字形差异是改不掉的

`index.html` 剩下那 10.70 的差距，主要集中在一行标题文字上（单块 mean 45.9）。看上去像 CSS 没调好，实际上不是。

**决定性实验**：在那一行上穷举本机全部可用的组合 —— 5 款中文字体 × 3 字号 × 3 字重 × 2 字距 = **90 组**，每组截图、比对、记分。

结果：**该行文字的可达下限是 mean 37–39**。再往下调不动，因为原图用的是 iOS 苹方，本机没有；思源黑体（Noto Sans SC）在字形层面就不一样，字重、字面率、笔画粗细分布都不同。这不是 CSS 能解决的。

这个结论很重要：它把一个"看起来还能优化"的问题，变成了"已被证伪、可以停手"的结论。**知道哪里到顶了，和知道哪里还没做，一样值钱。**

## 六、CSS 策略：为什么几乎全用绝对定位

打开任何一个页面的 `<style>`，会看到大量 `position:absolute;left:13px;top:284.43px`。

这是刻意的取舍：

- **目标是一比一还原**，不是做响应式组件库。绝对定位能精确复现原图的间距关系，不受盒模型、margin 折叠、flex 分配的影响
- 换回 flex/grid 会引入一堆隐式间距，反而更难对齐到 0.01px
- 代价是：**不可维护、不可复用、不能换屏幕尺寸**

真要做产品，这套做法是反面教材。但做"还原度验证"和"视觉回归测试"，它是最直接的。

`common.css` 里放的是跨页面共用的部分：状态栏、导航栏、tabbar、字体栈。

## 七、可交互部分

静态复刻只是第一步，本项目还做了可以真的操作的部分：

- **列表数值可点改**：点击数字直接编辑，失焦/回车落定，非法输入回滚，顶部合计实时重算
- **增删条目**：长按标题区域 1.5 秒进入编辑模式，右上角出现删除按钮，底部出现「＋ 新增一条」
- **持久化**：所有改动写入 `localStorage`，按年份分键，刷新和切页都保留
- **页面跳转链路**：首页卡片 → 筛选页 → 列表页 → 详情页，返回键带回参数

编辑入口做成"长按隐藏区域"，是为了不给静态还原界面加多余的视觉元素。

## 八、从网页到 APK

用 Capacitor 把 `www/` 目录包成安卓应用：

```bash
npx cap sync android          # 把 www 同步进 android/app/src/main/assets/public
cd android && ./gradlew assembleDebug
```

产物在 `android/app/build/outputs/apk/debug/app-debug.apk`。

环境要求：JDK 17、Android SDK（`compileSdk` 按 Capacitor 版本要求，本项目踩过 `androidx.core 1.15` 要求 compileSdk 35 的坑，最后降到与 34 兼容的版本组合）。

页面本身是固定 `393×852` 的，真机上会按实际屏幕缩放显示，不是自适应布局。

---

## 九、这套方法能迁移到哪

把"截图"换成"设计稿"或"旧版页面"，整套闭环照样成立：

- **视觉回归测试**：每次改动后自动截图比对，差异超阈值就失败
- **设计稿验收**：拿到 Figma 导出图，能量化"开发实现和设计稿差多少"
- **遗留系统重写**：老页面没有源码，只有截图，用它做逐像素对齐
- **跨端一致性**：iOS 和 Android 两版截图互比，找不一致处

核心不是某个工具，是那个**可测量的反馈环**。
